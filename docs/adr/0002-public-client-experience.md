# One Client: construct, `on`, `rest`, `connect`, interaction HTTP handle

Applications construct a single **Client**. Gateway lifecycle is `connect` / `disconnect`; dispatch uses Discord `t` strings via `on`; typed HTTP lives on `client.rest`; HTTP Interactions Endpoint URL traffic enters through `handleInteractionRequest`. Sharding is a constructor option (`recommended` or `{ id, count }`), not a second product. Transport, session, **Bucket**s, and **Decode** stay behind that seam.

**Considered options:** a three-entry Client whose only inbound verb is overloaded `receive`; a public kit (`ClientBuilder`, `Receive`, `ShardPlan`, injected `RestHttp`, cache port); flattening every REST operation onto `Client` with `run(dispatchTable)` as the guild-bot centre; injecting a Discord I/O port on `ClientOptions`. The first is deep but makes HTTP ingest and late handlers awkward. The kit is flexible and leaks fetch/cache before those tickets exist. Flattened REST plus a blocking `run` table is excellent for a 20-line ping bot and hostile to plugins and REST-only autocomplete. A public I/O port makes every bot an adapter assembler.

**Consequences:** REST-only bots omit intents and never `connect`. HTTP interactions do not require Gateway; the process HTTP server stays with the caller (scriptc has no LLVM HTTPS listener in core). `handleInteractionRequest` takes a raw body string and constructor `publicKey`; **Interaction signature** verify is [Choose how HTTP Interactions signatures verify on the static tier](https://github.com/Ermianr/moon-discord/issues/15). Discord’s mutex still forbids Gateway `INTERACTION_CREATE` plus the Interactions Endpoint URL on the same application. Tests share this Client interface; live `fetch` / RFC 6455 are internal adapters, not constructor options. Optional **Cache** is an opt-in constructor policy, not managers on this seam ([Choose the optional cache boundary](https://github.com/Ermianr/moon-discord/issues/11)).
