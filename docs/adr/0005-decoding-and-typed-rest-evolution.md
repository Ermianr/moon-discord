# Hand-owned inbound/outbound models; copy-decode; hatch stays unknown

Discord JSON is open and scriptc records are exact, so **Decode** copies known fields into closed **inbound model**s and never treats `JSON.parse` as a struct. **Outbound model**s are a separate type family for typed **Rest** bodies and queries. Extra inbound keys are dropped. `any` stays out. The **Rest hatch** returns `unknown` on success. **Unknown dispatch** (unknown `t`, or known `t` with a failed payload Decode) is observed on `Client.onUnknownDispatch`, not `on(t)`. Community OpenAPI is not the schema.

**Considered options:** generate parse-ready records from Discord’s unofficial OpenAPI; one shared resource type for events and Rest writes; branded Snowflakes; keep extra JSON on every struct; fail or kill the Gateway session when a known `t` payload does not match. Those either hit SC2002/`any`, lie about PATCH null vs omit, or drop events the 1.0 promise must emit.

**Consequences:** [Choose the public Client experience](https://github.com/Ermianr/moon-discord/issues/4) gains `onUnknownDispatch`. Typed Rest methods are the public source of truth (an internal operations table may generate names later). Discord JSON error `{ code, message, errors?: unknown }` is an inbound model thrown as `DiscordHttpError` ([Define failure, cancellation, and backpressure semantics](https://github.com/Ermianr/moon-discord/issues/12)). Header-level Gateway Decode failure stays with [Define Gateway lifecycle and sharding semantics](https://github.com/Ermianr/moon-discord/issues/9). Detail: `docs/research/decoding-and-typed-rest-evolution.md`.
