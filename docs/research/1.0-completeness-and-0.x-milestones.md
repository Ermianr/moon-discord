# 1.0 completeness and pre-1.0 milestones

**Issue:** [Define 1.0 completeness and pre-1.0 milestones](https://github.com/Ermianr/moon-discord/issues/5)  
**Decision date:** 2026-09-06  
**ADR:** `docs/adr/0003-1.0-completeness-and-0.x-milestones.md`  
**Inventory:** `docs/research/discord-api-v10-bot-core-obligations.md`

## Question

Given the applicable Discord bot-core inventory, what completeness promise defines `1.0`, and what coherent capability milestones precede it during `0.x`?

## Answer

`1.0` is **protocol-complete guild-bot coverage**: the official v10 Gateway and rate-limit machine, every official **Dispatch** `t` (and unknown `t` without killing the session), typed **Rest** for the guild-bot working set plus remaining guild-admin Bot-token operations, multipart on documented upload routes, and a **Rest hatch** for everything else. It is not a literal dump of every Bot-token row in the inventory.

The SemVer tag `1.0` is that capability plus packaging, performance, and failure gates from other tickets. This note does not invent those gates.

Public `0.x` artifacts follow four capability cuts so static binaries can be validated before the tag. Exact `0.1` / `0.2` numbers and CI belong to [Choose the delivery sequence and release gates](https://github.com/Ermianr/moon-discord/issues/13).

## 1.0 capability promise

### In

- Gateway JSON (`?v=10&encoding=json`, no transport compression): Hello, Identify, Heartbeat/ACK/zombie close, Resume, Invalid Session, Reconnect, documented close-code resume-vs-new-session behavior, Identify concurrency / session-start limits.
- **Intents** on Identify, including privileged intents as flags the application may set; the library does not require them.
- Sharding: Get Gateway Bot `shards`, Identify `[id, count]`, guild membership formula, `max_concurrency` buckets, events without `guild_id` on shard 0.
- HTTP rate limits from headers and 429 bodies (**Bucket** + global 50 rps, invalid-request tracking). Interaction callback/followup routes stay exempt from that global cap as Discord documents.
- **Dispatch**: decode and emit every official `t`, including `ENTITLEMENT_*` and `SUBSCRIPTION_*`, `VOICE_STATE_UPDATE`, `VOICE_SERVER_UPDATE`, and Gateway `RATE_LIMITED`. Undocumented `t` becomes **unknown dispatch** after header **Decode**; the session stays up.
- Interaction **receive** in `1.0`: Gateway `INTERACTION_CREATE` only. Initial HTTP callback (3s) and followups are required. Application command CRUD (Bot token) is in.
- Guild-Gateway **send** besides session internals: Presence Update, Voice State Update (opcode 4; not Voice protocol), Request Guild Members, Request Soundboard Sounds, Request Channel Info.
- Typed **Rest** for the surfaces in the next section, including `files[n]` on Create/Edit Message, webhook execute/edit, Create Interaction Response, and other routes that document attachments.
- **Rest hatch** for new, undocumented, deferred, or deprecated routes. The hatch is not a substitute for a promised typed method.
- REST-only applications: no Gateway `connect`, no cache. Cache stays optional and non-identity.

### Guild-bot working set (typed Rest)

Messages, channels, threads; guilds, members, roles, bans; users and DMs (bot-applicable routes); application commands except Edit Application Command Permissions; incoming webhooks except Slack/GitHub execute; audit log; auto moderation; invites except target-user CSV/jobs; guild emojis and stickers; scheduled events; stage instances; voice **resource** (REST, not Voice protocol); polls; Get Gateway and Get Gateway Bot; Get/Edit Current Application and Get Current Bot Application Information.

### Guild-admin Bot-token Rest also in 1.0

Guild templates (listed template routes; not unverified create-guild-from-template); onboarding; incident actions; prune; integrations; widget and vanity URL; application emojis; application role-connection **metadata** (bot token only); soundboard CRUD **except** Send Soundboard Sound; Search Guild Messages.

### Out of the 1.0 promise

| Surface | Disposition |
| --- | --- |
| HTTP Interactions Endpoint URL (Ed25519 ingest) | `1.x` completeness. Client may still expose `handleInteractionRequest` ([Choose the public Client experience](https://github.com/Ermianr/moon-discord/issues/4)); verify path is [Choose how HTTP Interactions signatures verify on the static tier](https://github.com/Ermianr/moon-discord/issues/15). |
| Monetization REST (entitlements, SKUs, subscriptions) | `1.x`. Dispatch for those resources still ships in `1.0`. |
| Invite target-users CSV/jobs; Slack/GitHub webhook execute | `1.x`. |
| Outgoing Webhook Events (`APPLICATION_AUTHORIZED`, …) | `1.x`; not a Gateway substitute. |
| Send Soundboard Sound | After Voice protocol exists (Voice remains out of this product). |
| Edit Application Command Permissions | Needs Bearer; omit typed method. |
| Create/Delete Guild / create-from-template | Omit while UNVERIFIED on current Discord resource pages. |
| Group DM add/remove recipient; Add Guild Member with a user access token | Omit (not Bot-token-only guild-bot). |
| Deprecated pin routes and Modify Current User Nick | Omit typed methods; hatch if Discord still serves them. |
| Lobby, Application Identity Profile, Activities instance as product | Out of this product, same as the map. |
| Voice protocol, user tokens/selfbots, general OAuth2, discord.js parity, WASI, runtime npm / `--dynamic` | Out of scope (map). |

## Pre-1.0 capability cuts

Each cut is a public validation artifact (published `0.x`). Order of engineering work and release gates: ticket 13.

| Cut | Capability | Representative shape |
| --- | --- | --- |
| 1. Static REST transport | LLVM `fetch`, User-Agent, Bot auth, JSON bodies, **Bucket** + global 50 rps, Get Gateway / Get Gateway Bot, **Rest hatch**. No Gateway. | REST-only binary. |
| 2. Gateway session | RFC 6455 over `tls.connect`, Hello/Identify/Heartbeat/Resume/close codes, Ready/Resumed, **Decode** `unknown` → structs. No dispatch dropped: unofficial `t` is **unknown dispatch**. | Session binary; JSON, no `compress`. |
| 3. Usable guild-bot | Typed Rest + typed **Dispatch** for the working set; `INTERACTION_CREATE` + 3s callback + followups; application command CRUD. **JSON-only** (no attachments). | Ping/command or message bot without files. |
| 4. Scale to 1.0 capability | Sharding and Identify concurrency; remaining official `t` types; remaining `1.0` Rest (guild-admin list); multipart uploads ([Choose a static-tier encoding for Discord multipart REST](https://github.com/Ermianr/moon-discord/issues/14)). | Sharded guild bot with attachments. |

`1.0` as **capability** is cut 4 done against this note. The SemVer tag also needs [Choose the packaging and artifact contract](https://github.com/Ermianr/moon-discord/issues/6), [Set the performance contract](https://github.com/Ermianr/moon-discord/issues/10), [Define failure, cancellation, and backpressure semantics](https://github.com/Ermianr/moon-discord/issues/12) (`docs/research/failure-cancellation-and-backpressure.md`), and ticket 13.

## Explicit non-decisions

- Version numbers, changelog policy, and CI command lists (ticket 13).
- Ed25519 / FFI / later crypto lowering (ticket 15).
- Multipart byte layout is resolved: [Choose a static-tier encoding for Discord multipart REST](https://github.com/Ermianr/moon-discord/issues/14) (`docs/research/static-tier-multipart-encoding.md`).
- Public **Client** verb set (already [Choose the public Client experience](https://github.com/Ermianr/moon-discord/issues/4)).
- Optional cache (resolved: [Choose the optional cache boundary](https://github.com/Ermianr/moon-discord/issues/11); not a `0.x` cut gate).
